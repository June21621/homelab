# 0005. CI는 GitHub Actions 호스티드 러너 + homelab의 재사용 워크플로

- 상태: 채택 (2026-11-03)

## 맥락

앱 코드가 바뀌면 테스트 → 이미지 빌드 → 레지스트리 push → 배포 태그 갱신까지 자동으로 이어져야 한다.
빌드를 어디서 돌릴지가 문제다. 미니 PC는 16GB 한 대이고 기반 컴포넌트 예산이 4GB 안팎이다(ADR 0002).
이미지 빌드는 순간적으로 CPU·메모리를 크게 쓰고, 서비스가 도는 노드에서 하면 서비스가 같이 느려진다.

서비스는 고정하지 않고 필요할 때 늘린다. 앱 repo가 늘 때마다 빌드 절차를 복사하면 repo마다 조금씩 달라진다.

## 결정

- GitHub Actions **호스티드 러너**에서 빌드한다. 미니 PC에는 러너·CI 서버를 두지 않는다
- 공통 절차는 homelab의 **재사용 워크플로** `.github/workflows/build-and-bump.yaml`(`workflow_call`) 하나에 둔다.
  앱 repo는 테스트 job과, 이 워크플로를 `uses:`로 부르는 몇 줄만 가진다
- 이미지는 GHCR(public), 태그는 커밋 SHA 40자. `latest`나 덮어쓰기 태그는 쓰지 않는다
- main 빌드만 push하고 **빌드 증명서**(`actions/attest-build-provenance`)를 붙인다. PR 빌드는 Dockerfile이 깨지지 않았는지만 본다
- 액션은 전부 커밋 SHA로 고정하고, 2주 이상 된 버전만 쓴다. job마다 필요한 권한만 준다(`permissions: {}`가 기본)

## 검토한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 미니 PC에 Jenkins 또는 자체 호스팅 러너 | 빌드 캐시가 로컬에 남음, 외부 의존 없음 | 빌드 부하가 서비스 노드에 걸림. 러너가 클러스터 안에 있으면 털렸을 때 클러스터에 바로 닿음. Jenkins는 메모리 수백 MB 상주(방향 전환 때 제외) |
| GitLab CI | 파이프라인 기능이 풍부 | 코드가 GitHub에 있어 미러링이 필요. 러너를 결국 어딘가에 둬야 함 |
| 앱 repo마다 워크플로 전체 복사 | 앱마다 자유롭게 바꿈 | 보안 설정(SHA 고정·권한)이 repo마다 어긋남. 증명서 검사에서 "우리 워크플로"를 하나로 지정할 수 없음 |
| 클러스터 안 빌드(Kaniko, BuildKit 파드) | 레지스트리 접근을 클러스터가 통제 | 빌드 부하·메모리가 여전히 미니 PC에 걸림 |

## 결과

- 미니 PC에는 빌드 부하가 없다. portfolio 빌드·push·증명서는 약 40초(2026-11-12)
- **증명서의 서명 워크플로가 이 파일 하나**라서, 태그 PR 검사(ADR 0007)가 "우리 워크플로로 앱 repo main에서 빌드된 이미지인가"를 확인할 수 있다
- 재사용 워크플로 안의 `github.sha`·`github.repository`는 **호출한 앱 repo의 값**이다. 실행·로그·Actions 사용량도 앱 repo 쪽에 쌓인다
- homelab이 public이어야 다른 repo가 별도 설정 없이 호출할 수 있다. public repo의 Actions 로그는 누구나 보므로 비밀값·내부 정보를 출력하지 않는다
- GitHub 장애나 무료 사용량 한도에 배포가 묶인다. 급하면 사람이 태그 PR을 직접 열 수 있다(그 경로는 Task 5에서 확인)
- 베이스 이미지도 다이제스트로 고정한다. `python:3.12-slim` 같은 움직이는 태그 때문에 코드는 그대로인데 이미지 내용물이 바뀐 일이 있었다(2026-11-11)
