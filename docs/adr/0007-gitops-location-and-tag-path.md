# 0007. gitops는 homelab 안에, 배포 태그는 봇 PR + 검사 통과 시 자동 병합

- 상태: 채택 (2026-11-13)

## 맥락

앱이 빌드되면 "어느 버전을 배포할지"(이미지 태그)를 Git에 써야 ArgoCD가 가져간다(ADR 0006).
누가, 어디에, 어떤 권한으로 쓰는지가 이 결정이다.

위험은 **앱 repo가 털리는 경우**다. 앱 repo의 CI는 homelab에 쓸 자격 증명을 갖게 되는데, 그게 새면
공격자가 `ansible/`·`terraform/`·`.github/workflows/`나 다른 앱 설정까지 바꿔 main에 넣을 수 있다.
반대로 매번 사람이 태그 PR을 병합하면 안전하지만 "앱 push → 사람 손 없이 배포"가 안 된다.

## 결정

**위치**: 배포 설정은 별도 repo가 아니라 homelab repo의 `gitops/`에 둔다. 인프라 코드(Ansible·Terraform)와 같은 곳에서
리뷰·보호 규칙·검증 기록을 한 번에 관리한다.

**태그 갱신 경로**

1. 앱 repo main 빌드가 끝나면 재사용 워크플로의 bump job이 **GitHub App**(`june21621-tag-bump`)의 1시간짜리 토큰을 받는다.
   App은 homelab에만 설치했고 권한은 Contents·Pull requests 쓰기뿐, **Workflows 권한은 없다**
2. homelab main의 `scripts/bump-tag.sh`로 `gitops/apps/<앱>/overlays/*/kustomization.yaml`의 `newTag:` 한 줄만 바꿔 PR을 열고,
   자동 병합(squash)을 예약한다. 같은 앱의 이전 태그 PR은 닫는다
3. 필수 검사 두 개가 통과해야 GitHub이 병합한다(ruleset, Terraform으로 관리, 우회 계정 없음)
   - `tag-pr-guard`: 봇 PR이면 파일 경로·바뀐 줄·SHA 일치·**빌드 증명서**(우리 재사용 워크플로, 앱 repo main, 그 커밋)를 확인.
     사람 PR은 바로 통과(사람이 직접 병합)
   - `static-checks`: pre-commit, 렌더 검사, 테스트, terraform validate
4. 필수 검사는 GitHub Actions 앱(`integration_id` 15368)이 보고한 것만 인정한다

**PR 브랜치 코드를 실행하지 않는다.** `tag-pr-guard`는 base(main) 커밋을 체크아웃해 검사기와 설정(`gitops/image-sources.yaml`)을
읽고, PR 변경분은 API로 받은 diff 텍스트로만 다룬다. App은 워크플로 파일은 못 바꾸지만 `scripts/tag_pr_guard/`는 바꿀 수 있으므로,
PR 쪽 검사기를 실행하면 "무조건 통과"로 바꿔치기할 수 있기 때문이다. 원칙: **검사받는 쪽이 검사 도구를 바꿀 수 없어야 한다.**

## 검토한 대안

| 대안                               | 장점                          | 버린 이유                                                                                          |
| -------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------- |
| 배포 설정을 별도 repo(`homelab-gitops`) | 권한을 repo 단위로 나눔             | repo·보호 규칙·워크플로가 두 벌. 혼자 운영하는 규모에선 관리 비용이 이득보다 큼. 같은 repo여도 경로 검사로 범위를 좁힐 수 있음                 |
| ArgoCD Image Updater             | 레지스트리를 보고 태그를 알아서 갱신, 코드 적음 | 클러스터 안 컴포넌트가 Git 쓰기 권한을 가져야 함. 레지스트리에 이름표만 같은 다른 이미지가 올라오면 그대로 배포. 변경이 PR·검사 기록으로 안 남음. 메모리 추가 |
| 앱 CI가 homelab main에 직접 push      | 가장 빠름                       | main 보호와 정면 충돌. 자격 증명이 새면 바로 main                                                              |
| 개인 토큰(PAT)으로 PR                  | 설정 간단                       | 내 계정 권한이 오래 사는 키로 앱 repo에 들어감. 권한을 repo·기능 단위로 못 좁힘                                            |
| `GITHUB_TOKEN`으로 PR              | 키 관리 없음                     | 다른 repo(homelab)에 쓸 수 없고, 이 토큰으로 연 PR은 검사 워크플로를 깨우지 못해 필수 검사를 영영 통과 못 함                        |
| 태그 PR도 사람이 매번 병합                 | 가장 안전                       | "사람 손 없이 배포" 목표와 충돌                                                                            |

## 결과

- 앱 병합 → prod 새 파드 8분, 사람 개입 0(2026-11-12)
- 봇 자격 증명이 새도 할 수 있는 일은 "태그 한 줄을 **우리가 빌드한 다른 이미지**로 바꾸는 것"뿐이다.
  위조 봇 PR 3종(다른 파일, 같은 파일 다른 줄, 검사기 수정)은 모두 병합이 막혔고, 워크플로 수정은 push 단계에서 GitHub이 거부했다
  (`docs/verification/2026-11-13-tag-pr-guard.md`)
- 모든 배포가 PR과 검사 기록으로 남고, 롤백은 `git revert`
- **한계: `pull_request` 이벤트의 워크플로 파일은 PR 쪽 것이 쓰인다.** 봇은 Workflows 권한이 없어 못 바꾸지만,
  사람이 연 PR은 검사 워크플로 자체를 바꿔 스스로 통과시킬 수 있다. 사람 PR은 사람이 병합하므로 리뷰가 방어선이다.
  `pull_request_target`으로 바꾸면 base 쪽 워크플로가 쓰이지만, 쓰기 권한 토큰으로 PR 코드를 만지게 되는 더 흔한 사고 경로라 택하지 않았다
- 검사기를 처음 넣는 PR은 main에 검사기가 없어 반드시 실패한다(실패 쪽으로 닫힘). 보호 규칙을 켜기 전에 병합해야 한다
- 이전 태그 PR 닫기는 PR 작성자(App)와 브랜치 이름(`bump/<앱>-`)으로 고른다. 사람이 같은 이름 규칙의 브랜치를 쓰지 않는다
- 봇 커밋은 서명 검증이 false다. 서명 필수 규칙은 걸지 않았다
